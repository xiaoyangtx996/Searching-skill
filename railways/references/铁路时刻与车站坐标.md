# 铁路时刻与车站坐标（本地表 + 12306/rail.re 接口）

本文件是 `railways/SKILL.md` 的**旁挂补充**：那份 SKILL.md 讲「线索 → 结论」的判读规则，
这里讲**能查的数据和能跑的脚本**。

> 为什么单独一个文件：`railways/SKILL.md` 由外部 darwin 流程生成（`darwin-results.tsv`、`<!-- darwin-wrapper:v1 -->`），
> 直接改正文下次重跑会被覆盖。所以新内容都放这里，SKILL.md 只留一行指针。

素材来源：用户的路路通 Web 复刻（`D:\lltskb\web`）。取出对**定位**有用的部分，
其余（Leaflet 地图、余票界面、Node 服务）不进技能。

## 1. 三件事，先看要哪个

| 手里有什么 | 用什么 | 网络 | 得到什么 |
|---|---|---|---|
| 照片里有**站名牌** | `clues.py lookup station <站名>` | ❌ 本地 | 该站坐标 + 电报码 + 所属城市 |
| 照片大致范围已知，想**看附近有哪些站** | `clues.py lookup station --near lat,lon` | ❌ 本地 | 最近的若干站 |
| 照片里有**车次号** | `train.py stops <车次> --date D --from X --to Y` | ✅ 12306 | 该车沿途经停站 + 每站坐标 = **一条走廊** |
| 照片里有**车型/涂装** | `train.py emu <车次>` | ✅ rail.re | 车型、车组号、运用日期 |
| 要**更新车站表** | `train.py stations --out ...` | ✅ 12306 | 最新站名/电报码/拼音/城市 |

**零网络的两条优先用。** 联网的两条是"锦上添花"，12306 接口变更时会失效（见第 5 节）。

## 2. 车站坐标表（本地，零网络）

`geo-sleuth/data/cn_stations.json`，3404 站。**每个字段的可信度不一样，必须区分**：

| 字段 | 来源 | 可信度 |
|---|---|---|
| `name` 站名 | 12306 `station_name.js` | ✅ **权威** |
| `code` 电报码 | 12306 | ✅ **权威**（如 北京南 = `VNP`） |
| `py` / `abbr` 拼音简拼 | 12306 | ✅ 权威 |
| `city` 所属城市 | 12306 | ✅ **权威** |
| `lat` / `lon` | OSM 经 Photon 匹配 | ⚠️ **分档，见下** |

### 坐标质量分档（`coord_quality`）

| 档 | 数量 | 含义 | 怎么用 |
|---|---|---|---|
| `verified` | 2990 | 同城中位数自校验通过 | 正常线索 |
| `unverified` | 204 | 单站城市 / 行政区中心兜底 | 弱线索，可能偏几公里 |
| `suspect` | 156 | **同名异地误匹配** | **默认不用**，仅 `--include-suspect` 时给 |
| `none` | 54 | 无坐标（境外站 + 极小乘降所） | 只能给城市 |

**为什么要分档**：Photon 按**站名**搜坐标，而很多站名是**乡镇名**（黄村、沙河、亚布力、景泰…），
于是匹配到了同名的地方。实测最严重的偏差：

| 站名 | 标称城市 | 错误坐标 | 真址 |
|---|---|---|---|
| `景泰` | 甘肃白银 | 39.86, 116.40 | ❌ 这是**北京** |
| `黄村` | 北京 | 23.12, 113.41 | ❌ 这是**广州** |
| `南翔北` | 上海 | 22.87, 113.49 | ❌ 这是**广东** |
| `民丰` | 新疆和田 | 31.60, 120.30 | ❌ 偏离 3702 km |

**规律**：错误坐标大量落在珠三角（22.6, 113.9）和长三角（31, 121）——那是同名大站所在。
所以**反查时 `suspect` 站必须剔除**，否则会给出一堆假邻站。

```bash
# 正查（单条）
py geo-sleuth/scripts/clues.py lookup station 北京南
py geo-sleuth/scripts/clues.py lookup station VNP      # 电报码也行
py geo-sleuth/scripts/clues.py lookup station bjn      # 拼音简拼（有歧义时列多个）

# 反查最近站（默认跳过 suspect）
py geo-sleuth/scripts/clues.py lookup station --near 39.90,116.40 --limit 5
py geo-sleuth/scripts/clues.py lookup station --near 39.90,116.40 --include-suspect   # 对比用
```

### 数据质量校验（可复现）

```bash
py geo-sleuth/scripts/qa_stations.py "D:/lltskb/web/data" data/station_qa.json   # 自校验，出可疑清单
py geo-sleuth/scripts/build_stations.py "D:/lltskb/web/data" data/cn_stations.json data/station_qa.json
```

`qa_stations.py` 用**同一城市的车站应彼此接近**做自校验（不依赖外部城市坐标表）：
按 `city` 分组算坐标中位数，偏离超过阈值的标 `suspect`，城市样本 <3 的标 `unverified`。

## 3. 12306 公开接口（联网，免登录）

三个接口，都是 12306 官方 OTN 公开接口，**不需要登录**：

| 接口 | 用途 |
|---|---|
| `/otn/resources/js/framework/station_name.js` | 车站表（站名/电报码/拼音/简拼/城市）—— **最稳** |
| `/otn/czxx/queryByTrainNo` | 车次 → 经停站序列 —— **定位价值最高** |
| `/otn/leftTicket/{endpoint}` | 余票（含发到站、时刻）—— 用来拿到车次内部编号 |

### 两个必须知道的机制（这是接口能长期可用的关键）

**① 必须带 Cookie**
先请求 `/otn/leftTicket/init`，从中收 `JSESSIONID`、`BIGipServerotn` 等初始 Cookie。

**② endpoint 会变，必须动态解析**
余票接口名历史上变过 `query` → `queryX` → `queryZ` → `queryG`。
正确做法是从 init 页面里解析：

```javascript
var CLeftTicketUrl = 'leftTicket/queryG';
```

`train.py` 里的 `_refresh_session()` 就做这件事，并在接口失效时**刷新重试一次**。
**这是路路通 Web 里最有价值的一段工程代码**——它让接口变更不会直接把功能打死。

### 实测输出

```bash
py geo-sleuth/scripts/train.py stops G9 --date 2026-10-02 --from 北京南 --to 上海虹桥
```
```
G9  2026-10-02  经停 5 站
  01 北京南      到 ----   发 10:00  停 ----  39.8635,116.3726
  02 济南西      到 11:23  发 11:26  停 3分钟  36.6691,116.8883
  03 南京南      到 13:24  发 13:26  停 2分钟  31.9730,118.7916
  04 无锡东      到 14:05  发 14:07  停 2分钟  31.5982,120.4548
  05 上海虹桥     到 14:35  发 14:35  停 ----  31.1961,121.3161
```

**经停站序列每站自带坐标**（verified 站才显示坐标）。这就是一条**走廊**：
知道照片里是哪趟车 + 大致时段，就能把范围从"全国铁路网"缩到"这条线上的几个站"。

## 4. rail.re（联网，免登录）

`https://api.rail.re/train/{车次}` 返回该车次**近 30 天**的车底运用记录：

```json
[{"date":"2026-10-01 14:19","emu_no":"CR400AFG2217","train_no":"G107"}, ...]
```

从 `emu_no` 去掉末尾数字得车型：`CR400AFG2217` → **`CR400AFG`**。

```bash
py geo-sleuth/scripts/train.py emu G107
# G107  车型 CR400AFG  车组号 CR400AFG2217  运用日期 2026-10-01 14:19  （近 30 条记录）
```

**定位用途**：配合 `railways/SKILL.md` 已有的规则
「特定涂装或颜色的动车组 → 可锁定其配属的少数铁路局或区域」——
查到车型后可以进一步确定配属路局，收窄地域。

**限制**：只对 G/D/C 字头有效，普速（K/T/Z）没有动车组记录，属正常。

## 5. 已知限制与护栏

1. **站名/电报码/城市可信，坐标要分档看**（见第 2 节的 `coord_quality`）。
2. **`suspect` 坐标默认不返回** —— 这是防止"假邻站"污染候选，不要用 `--include-suspect` 找证据。
3. **12306 endpoint 会变** —— `train.py` 有动态解析 + 重试兜底，但若 12306 大改版仍可能失效。
   失效时**退回第 2 节的本地表**，定位能力主要丢的是"车次→经停站"，核心判读不受影响。
4. **余票接口当天才有数据** —— 查历史日期或未来过远的日期会查不到车次。
   找 `train_no` 只是手段，最终要的是 `queryByTrainNo` 的经停站。
5. **车次会改号/停运** —— 老照片里的车次可能已不存在，查不到不代表数据错。
6. **rail.re 是第三方** —— 数据来自 emu-log 社区，可能滞后或缺记录；查不到不等于该车没有配属。
7. **不要把"查到车次"当成"照片就在这条线上"** —— 车次只给走廊，具体站点还要靠画面线索
   （站台编号、雨棚、站房样式）落到某一个站。

## 6. 与其他技能的分工

| 技能 | 管什么 |
|---|---|
| `railways/SKILL.md` | 车型、雨棚、股道、路局等**判读规则**（线索 → 结论） |
| **本文件 / `train.py`** | **能查的数据**：车站坐标、车次经停站、车型 |
| `geo-sleuth/scripts/clues.py` | 统一查表入口（`station` 是新增的一种 kind） |
| `geo-sleuth/scripts/osm.py` | 现查 OSM 铁路（互补：OSM 有线路几何，这里只有站点） |

**联用**：`clues.py lookup station --near <候选坐标>` 反查最近车站 →
把车站名喂给 `osm.py` 查该站周边设施 → 进 `board.py` 候选盘。
